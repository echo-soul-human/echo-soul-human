## 2. 图片

### 2.1 存储与分发
```
Storage 桶：assets（公）/ user-media（私，签名 URL）
上传 → Edge Function validate → 服务端重编码 → 生成缩略图三档 → 落库路径
```
- **一律服务端重编码**（剥 EXIF，含 GPS；统一转 webp，动图保留原格式）。理由：安全 + 体积 + 一致性。
- 尺寸档：`thumb 128` / `card 480` / `full 1280`，长边封顶 1280（立绘再大对手机无意义，且流量是用户付的）。
- 动图（表情包）：GIF 保留；可选转 webp 动图省 60% 体积，但**安卓低端机解码 webp 动图有兼容坑**，实测后再定。
- 签名 URL 有效期：会话内图片 1 小时；广场公开图走公桶不设签名。

### 2.2 表情包导入（爱语已验证的刚需）
```
用户一次拖 20-200 张图 → 服务端批量：
  1. 校验格式与大小
  2. 自动命名（文件名去扩展名，无意义名回落"表情 N"）
  3. 可选：给每张生成一句"使用场景提示"（用于后面让模型知道什么时候发这张）
  4. 打包成 pack，可整包启用/停用
```
**关键设计**：表情包不只是"发出去的图"，还要能让**角色主动发表情**。做法：
- 每张表情带一个 `caption`（用户可改，默认自动生成）
- 对话时把启用包里的 `caption` 列表以**极短形式**注入 prompt 动态段（约 200-400 token）
- 模型输出特定标记（如 `[emoji:笑哭]`）→ 前端渲染成图片
- 【必做】注入的是 caption 列表而非图片本身，**不吃视觉模型、成本可控**。这是这个功能能便宜落地的关键。

⚠️ 包位上限是硬成本（Storage + 列表注入 token）。Free 20 张已经不小，别好心放大。

### 2.3 立绘与角色一致性
- 一个角色一个主立绘 + 可选多张"表情差分"（不同情绪显示不同图）
- 差分与情感标签绑定：`{ emotion: '开心', image: '...' }`
- **前端按情绪切换立绘**，情绪标签由模型输出的隐藏标记给出（不进正文显示）
- 这是沉浸感性价比最高的一招：不用生成图，只要用户传 4-6 张差分，效果立竿见影

### 2.4 图片生成（一期不做）
一期**不接图像生成**。理由：成本结构完全不同（单张 ¥0.1-0.5 量级）、需要独立计费、且用户自传立绘已能满足核心需求。放二期评估。

## 3. TTS

### 3.1 供应商与抽象
```
TTS Provider 抽象（与 LLM Provider 同构）：
  synthesize({ text, voice_id, emotion?, speed?, format? }) → audio url|bytes
```
候选：MiniMax（Talkie 用的就是它，情感表达是强项）、豆包/火山、阿里。
【必做】上线前实测三家的：中文情感自然度、首包延迟、单价、并发配额。**不照抄本文，也不照抄竞品。**

### 3.2 成本与计量（★必须单独算，不能混进 token 额度）
TTS 按**字符**计费，量级约 ¥0.5-2 / 万字符（待实测）。一条 200 字的回复 ≈ ¥0.01-0.04，**和一轮对话成本同量级**。

所以：
```
tts_credit 独立额度（与模型 credit 分账）
  ledger 新增 type：'tts_grant' / 'tts_consume'
  档位含每月 TTS 字符数：Lite 5万 / Pro 20万 / Pro+ 60万 / Ultra 不限（但限频）
```
⚠️ **绝对不要把 TTS 成本混进模型 credit**。混了之后 §3.3（分册-模型与计费）的成本反推会失真，看不出到底哪档在亏钱。

### 3.3 播放
- 音频文件**服务端缓存**（同文本+同音色+同情绪 → 复用，命中即零成本）。这是 TTS 最大的省钱手段，必做。
- 缓存键：`sha256(voice_id + emotion + normalized_text)`，存 Storage `tts-cache` 桶，LRU 30 天。
- 客户端：短音频 `MediaPlayer`，需要连续播放/队列时用 `ExoPlayer`
- 音频焦点：来电/其他 App 播放 → 暂停；耳机拔出 → 立即停
- 网页：`<audio>` + `MediaSession API`（锁屏控制）
- iOS Safari 自动播放限制：**必须由用户手势触发首次播放**，之后才能连播。"自动朗读每条回复"这个功能在 iOS 上第一次必须用户点一下，UI 要说明。

### 3.4 情绪标签与角色绑定
```
character_voices:
  character_id, voice_provider, voice_id, default_emotion, speed, pitch
emotion_map:  { '开心': {voice_variant, style}, '难过': {...} }
```
- 角色创建向导里第三步"选声音"，试听 3 秒
- 情绪切换由模型输出的隐藏标记驱动（与 §2.3 立绘差分共用同一套标记）
- **自定义音色导入**（Pro+ 以上）：用户填供应商的音色 ID。注意这会把用户引向需要独立账号的音色克隆服务，UI 要说清"音色由第三方提供，费用与授权自行负责"

### 3.5 流式与朗读的取舍
一期：**等 `done` 后再朗读整段**。
不做逐句流式 TTS 的原因：逐句切分容易切坏语气、调用次数翻倍、且缓存复用率暴跌（整段文本才能命中缓存）。
二期若要做，只在"通话模式"下开，且要重算成本模型。

## 4. 与记忆/检索的交互

- 图片消息**不进向量库**（一期不做图像 embedding）。但图片的 `caption` 进 `tsv`，能被关键词召回。
- 语音消息一期不存在（无 ASR）。
- 表情包被角色主动发出时，作为一条 `messages` 记录（`content` 存 pack+item 标识），**参与 RAG 的 episode 抽取**——"上次我发了那个哭的表情，TA 就哄我了"这类记忆是有价值的。

## 5. 上传内容的可见性与治理（产品功能项）

用户上传的立绘/表情包有四种可见性，**默认必须是仅自己**：
```
private   （默认）仅自己会话内可见
unlisted  拿到链接可见
community 进广场（需审核）
```
- 进 `community` 必须走后台审核队列（管理后台已定案 I8）
- 签名 URL 对 `private` 素材必须校验 `user_id`，**不能只靠"路径难猜"**
- 【必做】验收项：用 B 的 token 换 A 的素材签名 URL → 必须 403
