## 1. 内置模型接入

### 1.1 定案与待核实
用户 A2 定案：**内置只有 DeepSeek Flash 一档**，后续只跟 DeepSeek 最新的 Flash 类模型。

⚠️ 【必做】上线前必须到 DeepSeek 官方控制台核实三件事，**不要照抄本文件的数字**：
1. `model` 字段的准确字符串（厂商会改命名，"Flash" 是品类描述不一定是 API 值）
2. 实时单价（输入 / 输出 / **缓存命中** 三个价）
3. 上下文窗口与最大输出 token

本文件用的调研值：输入 `$0.14/M`、输出 `$0.28/M`（V4-Flash 档），缓存命中价可低至输入价的 **1/40 量级**。汇率按 7.1 折人民币。**这些只用于建立数量级直觉，不是定价依据。**

### 1.2 接入层
```
supabase/functions/chat/providers/deepseek.ts
```
- 单一 provider 实现，但**接口抽象成 `Provider`**（`stream(messages, opts): AsyncIterable<Delta|Usage>`）。理由：BYOK 要复用同一抽象，且将来跟 DeepSeek 新版只改一处。
- 必须解析并落库 `usage.prompt_tokens / completion_tokens`，以及 DeepSeek 返回的**缓存命中 token 数**（字段名以官方为准）。不落这个就无法核算真实成本，§3 的省钱主牌就成了盲飞。
- 超时：连接 10s、首字节 20s、流内静默 45s（无新 token 即判卡死）。
- 不做任何"重试到别的模型"的降级（A2 定案只有一个模型），失败就按 §9 矩阵处理。

## 2. 静态前缀规范（★省钱主牌，必须逐字执行）

DeepSeek 的上下文缓存是**自动前缀匹配**：请求前缀与之前请求完全一致的部分按缓存价计。所以省钱的全部工程含义就是一句话：

> **让前缀一模一样，一直一样。**

### 2.1 前缀分区（与架构 §4 一致）
```
[A] 平台层锁        全局唯一，跨所有角色、所有用户、所有轮次完全相同
[B] 角色层锁        角色发布后冻结，同角色所有用户所有轮次相同
[C] 半静态段        关系阶段描述 + 人设摘要，只在 stage 跃迁时变
─────────── 缓存边界（A+B 稳定命中；C 一天最多变一次）───────────
[D] RAG 召回片段    每轮变
[E] 携带历史        每轮变
[F] 本轮输入 + 时间戳 + 余额提示   每轮变
```

### 2.2 硬性禁令
| 禁止 | 原因 |
|---|---|
| 在 A/B/C 里拼**时间戳、用户名、余额、随机数、设备信息** | 立刻击穿缓存，成本涨 3.2 倍 |
| 在 A/B 里做 `trim()`/`normalize()` 之外的任何字符串处理 | 空白差异也会击穿 |
| 把"当前是第 N 轮"写进前缀 | 击穿 |
| 角色人设"热更新"（改了立即对老会话生效） | 击穿，且会让已发生的记忆与新前缀矛盾 |
| 把 RAG 片段插到历史之前 | 击穿（顺序变了） |

### 2.3 工程防线（不能靠自觉）
```
supabase/functions/_shared/prefix/
  platform-lock.md      ← 纯文本，A 段唯一来源
  role-lock.tpl.md      ← B 段模板，只允许 {{character_id}} 一个占位符，
                          且该占位符在构建期展开成静态映射表
```
CI 检查（`scripts/check-prefix.mjs`）：
1. A/B 段文件在 PR 里被改动 → **必须打 `prefix-break` 标签**，CI 强制在描述里写明预期成本影响，并触发一次命中率基线复测。
2. 扫描 `chat` 函数源码：任何 `Date.now()`、`new Date()`、`user.` 出现在前缀拼装路径上 → 直接失败。
3. `character_locks.static_hash` 与模板 hash 比对，不一致 → 失败。

### 2.4 命中率看板（P2 出口判据）
```
命中率 = usage_cached_tokens / (usage_prompt_tokens 中属于 A+B 的部分)
```
- 目标 **≥ 90%**。低于 80% 说明有人破坏了 §2.2，**这是线上事故级别**，因为它是静默亏钱。
- 按角色、按档位、按小时分桶看。新用户首次对话必然不命中（正常，别慌）。

## 3. 成本模型与校准

### 3.1 单轮成本（调研值，待实测覆盖）
| 组成 | token | 未命中 | 命中后 |
|---|---|---|---|
| A 平台锁 | 900 | ¥0.0009 | ¥0.00002 |
| B 角色锁 | 2,100 | ¥0.0021 | ¥0.00005 |
| C 阶段段 | 400 | ¥0.0004 | ¥0.0004 |
| D RAG 召回 | 1,200 | ¥0.0012 | ¥0.0012 |
| E 携带历史（Pro 档 48K） | 48,000 | ¥0.0480 | ¥0.0480 |
| F 本轮输入 | 120 | ¥0.0001 | ¥0.0001 |
| 输出 | 600 | ¥0.0012 | ¥0.0012 |
| **合计** | | **¥0.0539** | **¥0.0510** |

> ⚠️ 这张表暴露了一个比"缓存击穿"更大的事实：**E（携带历史）才是成本主体，不是前缀。**
> 前缀 A+B 只占未命中成本的 5.5%。所以缓存优化能救的是"轻量轮次"，真正决定毛利的是**携带量分档**。

### 3.2 由此得出的三条定价约束
1. **携带量是核心成本杠杆**，必须严格按档位截断（Free 8K / Lite 16K / Pro 48K / Pro+ 128K / Ultra 512K）。用户 B5 想卖"更长上下文"，卖 512K 就是每轮 ¥0.5 级别的成本——**Ultra 档的 322 轮/天如果都吃满 512K，毛利直接转负**。
   → 【必做】Ultra 的"512K 携带"必须是**上限而非默认**。默认携带 64K，用户手动拉高，且拉高时明示"每轮消耗约 ×N"。这是 §6 的截断策略要解决的。
2. **输出长度也是钱**。角色默认输出上限 800 token，`verbose` 人设才放到 1600。
3. **embedding 成本可忽略**（约 ¥0.5/M 量级），但**不能不管**：抽取记忆的调用要批量、要限频（每 8 轮一次），别每轮都抽。

### 3.3 校准闭环
```
每日任务：
  按档位聚合 Σcost_actual / Σcredit_consumed → 反推实际零售倍率
  若某档实际倍率 < 4.5×（定价假设是 6×）→ 告警：该档在亏钱
  若 < 3.5× → 自动在管理后台置顶，要求调参（改 plan_catalog 即可，不改代码）
```
这是把"定价"从一次性决策变成持续运营动作。**必做**，因为模型价格会变、用户行为会变。

## 4. BYOK 适配层

### 4.1 两协议差异表
| 维度 | OpenAI 兼容 | Anthropic |
|---|---|---|
| 路径 | `/v1/chat/completions` | `/v1/messages` |
| system | `messages[0].role='system'` | 顶层 `system` 参数 |
| 流式 | `data: {...choices[0].delta.content}` | `event: content_block_delta` + `data.delta.text` |
| 结束标志 | `data: [DONE]` | `event: message_stop` |
| usage | `usage.prompt_tokens` | `usage.input_tokens`（且流式下常在 `message_delta` 才给） |
| 最大输出 | `max_tokens` | `max_tokens` **必填** |
| 缓存 | 各家自定义 | `cache_control: {type:'ephemeral'}` 显式标注 |
| 错误体 | `error.message` | `type.error.message` |

### 4.2 适配实现
```ts
interface Provider {
  build(body: InternalReq): RequestInit
  parseSSE(frame: string): Delta | Usage | Done | null
  normalizeError(status: number, raw: unknown): AppError
  estimate(body: InternalReq): TokenEstimate    // 用于预冻结
}
```
- **Anthropic 的显式缓存要单独处理**：它需要给 system 块打 `cache_control`，命中后写入价 ×1.25、读取价 ×0.1。对 BYOK 用户是**帮他省钱**的功能，值得做，UI 上给"已为你启用 Anthropic 提示缓存"的开关。
- OpenAI 兼容侧各家实现差异大（豆包、Kimi、Qwen、OpenRouter、本地 Ollama），**不做逐家特化**，只保证标准协议 + 一个"自定义字段透传"高级面板。用户报不兼容再按频次决定要不要特化。

### 4.3 BYOK 的密钥处理
```
用户提交 Key → Edge Function 内信封加密 → byok_profiles.encrypted_key
读取：Edge Function 内解密 → 直接用于出网请求 → 明文不落日志、不进 error、不回客户端
客户端只见掩码：sk-****abcd（后 4 位）
```
- 主密钥 `BYOK_MASTER_KEY` 放 Supabase Secrets，**不入库、不进仓库**。
- 数据密钥逐条加密（不是全局一把），这样泄露一条不牵连全部。
- 【必做】提供"一键删除所有 Key"，且删除后 `byok_profiles` 行真删（不是软删）。
- 【必做】Key 校验用一次最小请求（发 "hi"，max_tokens=1），失败给可懂的中文原因（"这个 Key 没有权限"vs"地址不对"vs"网络不通"），**不要抛原始英文错误**——这是首次对话完成率的直接杀手。

### 4.4 BYOK 不扣额度，但要记账
`ledger` 写 `type='byok_usage'`、`amount=0`，用途：
- 反滥用统计（有人拿 BYOK 通道做批量转售）
- 成本归因（RAG 的 embedding 是我们出的钱，BYOK 用户也在消耗平台资源）
- 后续"BYOK 用户也要付能力费"的定价依据

## 5. 爱发电接入（★归因链路）

### 5.1 定案回顾与风险
用户 D5 定案：**OAuth + 订单比对全自动发放，不用二维码、不用兑换码、不做客服。**

⚠️ 【必做，阻塞项】上线前必须核实两件事，任一不成立就要回到 HANDOFF 附录 B 的 Q3 重定方案：
1. 爱发电是否开放**第三方 OAuth 登录**（调研显示社区有 OAuth SDK 实现，但需确认官方是否对个人创作者开放）
2. 是否有可查**指定用户订单/订阅记录**的开放 API（调研显示存在 `user_id` + 签名的开放接口，需确认能否查到"某用户对某商品的最新有效订单"）

### 5.2 归因方案（按可靠性分级）
```
L1（首选）爱发电 OAuth 登录
   用户点"用爱发电登录" → 拿到 afdian_user_id → 存 profiles
   → 轮询任务按 afdian_user_id 查订单 → 比对 plan_catalog → 发放
   归因 100% 可靠，无需用户做任何额外动作

L2（OAuth 不可用时）邮箱匹配
   爱发电订单里有赞助者邮箱 → 与我们注册邮箱比对
   问题：爱发电 API 是否返回邮箱、以及用户注册邮箱与发电账号邮箱不一致
   命中率估计 60-80%，需配"我付了但没到账"的自助重查按钮（不是客服，是让用户点一下触发重查）

L3（兜底）订单号自助回填
   用户在我们页面输入爱发电订单号 → 服务端查该订单 → 归因
   ⚠️ 这与用户拒绝的"兑换码"不同：兑换码是我们要发码，这里是用户复制自己的订单号。
   仍需用户确认是否接受（见 §11 Q1）
```
**推荐 L1 + L2 + L3 三层并存**，L1 不通自动退 L2，L2 查不到给 L3 入口。**全程无人工客服介入。**

### 5.3 轮询与发放
```
cron 每 60s：
  拉取近 2 小时内活跃订单（按 plan_catalog 里的商品过滤）
  → 对每单：
     select ... for update on profiles 行（防并发）
     若 orders.external_id 已存在 → 跳过（幂等）
     否则：insert orders → upsert entitlements（expires_at = max(现值, now) + valid_days）
          → ledger insert type='grant'
  → 未匹配到用户的订单 → unmatched_orders（仅后台可见，不打扰用户）
```
**关键细节**：`expires_at = max(现值, now()) + valid_days` —— 用户在未到期时又付一笔，应该是**顺延**而不是覆盖。做错这个会被投诉，且投诉完全合理。

### 5.4 文案约束（D1 定案，写进验收）
全站 grep 检查，**不得出现**：`月`（作为计费周期）、`自动续费`、`订阅中将于X日自动扣款`、`续费`（改为"续期"/"延长"）。
**必须出现**：有效期明确写"31 天"/"372 天"；到期前 3 天提醒；提醒文案不得用"失去 TA""TA 会忘记你"这类施压话术。

## 6. 携带量截断策略

架构 §7.3 的核心执行细节。目标：**用户觉得"它记得很久"，但每轮实际进 prompt 的量受控。**

```
需要携带的历史 token 预算 = 档位 carry_tokens 上限（默认值，用户可调高到上限）

装配顺序（从预算里倒扣）：
  1. A+B+C 前缀          固定，不参与裁剪
  2. D RAG 召回          top_k 条，按档位（4/6/8/12/20）
  3. E 历史              从最新往回装，装满剩余预算为止
     - 优先保留：最近 12 轮完整
     - 更早的：只保留用户消息 + AI 消息首句（压缩显示）
     - 再早的：丢弃（已由 RAG 覆盖）
  4. F 本轮输入          永不裁剪
```
**用户可感知的表现**：
- 拉到"记忆回顾"页能看到"TA 记得的 37 件事"（RAG 里捞的），而不是"能滚到最早的消息"
- 若用户手动把携带量拉到上限，明示"每轮消耗约 ×N，预计 XX 轮后用尽本档额度"

**这条是 D4/D6 冲突的解法，务必在 UI 上体现为"上限"而非"默认"**，否则 Ultra 档会亏（§3.2 第 1 点）。

## 7. 扣费时序（chat 链路里的账本调用）

```
1  估算本轮上限   estimate()：按档位 carry + 输出上限 + 前缀长度 → p_max
2  freeze_credit(p_user, p_max, request_id)      → 不足则直接 INSUFFICIENT_BALANCE，不调模型
3  落用户消息
4  并行 recall()
5  拼 prompt（§2 分区）
6  调模型，流式转发，累计实际 token
7a 成功 → settle_credit(freeze_id, 实际额, request_id)
        差额 refund_credit(ref 到同一 freeze_id)
7b 失败 → refund_credit(freeze_id, 全额, reason='model_error')
8  落 AI 消息（含 usage_*、cost_actual）
9  投 extract_jobs（异步）
```
**三条不变式**（每条都要写测试）：
1. `Σ(settle + refund_to_freeze) == Σ freeze` —— 没有钱凭空消失或产生
2. 任一 `request_id` 最多一条 `freeze`、最多一条 `settle`
3. 模型失败 ⇒ 用户余额净变化为 0

【必做】§3.3 的对账任务每日跑一次这三条不变式，不一致就告警并冻结该用户扣费（宁可停服务，不要错账）。

## 8. 限频与反滥用

| 维度 | 策略 |
|---|---|
| 单用户并发 | 同 `session_id` 串行；不同会话最多 2 并发 |
| 轮次频率 | 档位分级：Free 20 轮/时、Lite 60、Pro 200、Pro+ 400、Ultra 800 |
| 新账号 | 注册后 10 分钟内限 10 轮（防脚本批量注册薅体验额度） |
| 设备指纹 | `device_id` + UA + IP 三元组，异常聚集进后台队列 |
| Key 滥用 | 同一 BYOK Key 被 >20 个账号使用 → 提示（不封，因为家庭共用合理） |
| 体验额度 | ¥3 一次性，**注销不返还、换号不重发**（按 `device_id` + IP 双重判定） |
| Edge Function 出网 | 限制目标 host 白名单（DeepSeek + 用户配置的 BYOK 域名），防 SSRF |

⚠️ **SSRF 是 BYOK 架构的真实技术风险**：用户能填任意 endpoint，服务端就会往那个地址发请求，可能被用来打内网。必须做：
- 解析域名后校验 IP 不为内网/回环/链路本地段
- 禁跳转（`redirect: 'error'`）
- 出网超时与响应体大小上限
- 【必做】这一条进验收清单，不是可选项

## 9. 失败与重试矩阵

| 情况 | 服务端 | 客户端 |
|---|---|---|
| 连接失败 | 未产生 token → 全额退 | 静默重试 2 次（1s、3s 退避） |
| 首字节超时 20s | 全额退 | 重试 1 次，再失败提示"TA 那边有点挤，稍等一下" |
| 流中断 | 已生成部分**结算**（钱要认），消息标 `partial=true` | 保留已显示 + "继续"按钮（带 `message_id` 续接） |
| 上游 429 | 全额退 | 静默重试 3 次（指数退避，最长 30s） |
| 上游 401/403（BYOK Key 失效） | 全额退 | 明确提示"你的 Key 好像不能用了，检查一下"，给跳转配置页 |
| 余额不足 | 不调模型 | 弹额度页，文案见 §5.4 |
| 出戏校验失败 | 静默重生成 1 次（成本自己吃） | 用户无感 |
| 我们侧 5xx | 全额退 | 重试 1 次后提示 |

**原则**：**只要模型没产出，就不该收钱**。这条做到位，用户投诉会少一大半，也符合"不做客服"的运营约束。

## 10. 消耗可视化（把省钱做成卖点）

抖音第一痛点是"Token 太贵养不起"（8.7 万赞）。所以**不要藏成本，要把它做成产品功能**：

- 每条 AI 回复下方极细一行小字：`本轮 8.1K · 缓存命中 62% · 剩余额度 ¥12.88`（可关）
- 会话页顶部"本月已用 / 剩余 / 按当前速度还能聊 N 天"
- 设置页"成本优化"面板：
  - 携带量滑杆（默认 64K，拉到上限时明示消耗倍数）
  - RAG 召回条数
  - 输出长度偏好（简短/适中/详细）
  - "省额度模式"（自动降携带 + 降召回，牺牲一点记忆精度换 3 倍轮数）
- **BYOK 用户**：显示"本轮你花了约 XX token"，帮他算自己的账 —— 这是极有效的口碑点，因为"养不起"是他们的共同创伤

这面板本身就是抖音图文素材（"我做了个能看见花了多少钱的聊天软件"），零成本传播。
