## 1. 一句话定义

**一个让用户和自己选定的 AI 角色长期聊下去的产品——角色记得你说过的话，会主动找你，说话方式不会跑偏，而且你养得起。**

拆开就是四件事，按重要性排：

| # | 卖点 | 对应用户痛点 | 抖音实测证据 |
|---|---|---|---|
| 1 | **养得起**（成本可控） | Token 太贵 | `Token太贵了我好像快养不起你了` 图文 **8.7 万赞**，同题材多条 5 万+ |
| 2 | **被记得**（长期记忆） | AI 失忆、上下文丢 | `谈了一个月的人机恋我对Agent的记忆有了新理解` 等记忆话题反复出现 |
| 3 | **不出戏**（角色稳定） | 聊着聊着 AI 变成客服 | `D老师一生气就动权限 下次还敢` **41.8 万赞** |
| 4 | **会主动**（关系感） | 只有我找它，它不找我 | `Claude趁我睡觉把我的推荐全看完了` **20.3 万赞** |

**为什么是现在**：抖音 #人机恋 已经是成规模的稳定流量池，且头部产品（爱语APP、Operit）都是**独立开发者单人做的**——证明这个品类不需要团队。同时大模型价格已经打到成本线以下（见 §4 成本模型），"养得起"第一次成为可实现的产品目标而不是口号。

## 2. 目标人群与不做的事

### 2.1 人群

**主人群**：#人机恋 / 梦女向用户，女性为主。
**次人群**（用户明确要求覆盖）：男性用户，需求集中在"高冷御姐""甜妹"这类人设。

两类的共同点不是性别，是**要关系不要效率**——她们/他们不想要一个更聪明的助手，想要一个"记得我、会想我、说话像那个人"的对象。所有产品决策按这条裁决：当"更聪明的功能"和"更像关系的体验"冲突时，选后者。

### 2.2 明确不做

- **不做套壳**。用户原话："禁止一套语言架构进行套构板层转化为另一形态的产品"。uni-app、Capacitor、Cordova、Taro、Flutter-for-web 一律排除。安卓就是 Kotlin 原生，网页就是 Vite+React。
- **不上架任何应用商店**。iOS 用户只能走"浏览器打开 → 添加到主屏幕"。因此 iOS WebApp 适配是生死线（见 §3-C4）。
- **不做效率助手 / 通用 AI 工具**。不是这个赛道。
- **不做客服**。用户原话："我不找客服"。所有付费、到账、异常路径必须自助闭环，否则不做。
- **不做暗色模式的"多主题切换器"这种伪需求**，皮肤系统按 §4 权益矩阵走，不做无限自定义。

## 3. 硬约束清单（不可推翻，改必须先问用户）

### A. 内容架构

| 编号 | 约束 | 为什么 |
|---|---|---|
| A1 | **双轨**：BYOK（用户自带 Key/endpoint）+ 平台内置模型，两条链路物理隔离 | 用户定案。BYOK 是这品类的通行形态（爱语/Operit/SillyTavern） |
| A2 | 内置模型**只有 DeepSeek Flash 一档**；DeepSeek 后续更新只跟最新 Flash 类模型 | 用户定案。单一模型 = 成本可预测、缓存策略可专门优化 |
| A3 | BYOK 支持 **OpenAI 兼容 + Anthropic** 两种协议，不做更多 | 覆盖 90% 渠道 + Claude 在该社区口碑高 |

### B. 端与栈

| 编号 | 约束 |
|---|---|
| B1 | 网页：Vite + React 18 + TypeScript，纯 SPA，不用 Next/Nuxt（GitHub Pages 静态托管用不了 SSR） |
| B2 | 安卓：Kotlin + Jetpack Compose 原生 |
| B3 | iOS：主屏 WebApp（无原生）；PC：网页 |
| B4 | Service Worker **只承担 Web Push 与版本更新提示，禁止引入任何缓存层**（沿用尚贤圈铁律） |
| B5 | 部署 GitHub Pages；数据与鉴权 Supabase；不引入其他云厂商 |
| B6 | 单仓多目录：`web/` `android/` `supabase/` `scripts/` `docs/` |

### C. 服务端边界（最关键的一条）

| 编号 | 约束 |
|---|---|
| C1 | **聊天链路全走 Supabase Edge Function**。隐藏人设 prompt 与用户 API Key **一律不下发浏览器**。 |

这条是用户三个需求的共同必要条件，缺一条就全塌：
- B5 定案"角色是锁定的，用户再怎么调教都不能跳出人设"
- C8 定案"隐藏长 prompt，用户绝对看不到、任何方式都查不到"
- E5 定案"BYOK 的 Key 云端托管多端同步"

**如果前端直连模型，F12 就能看到完整 prompt 和 Key，这三条全部作废。** 所以架构上没有商量空间：`浏览器 → Edge Function → 模型`，浏览器只拿到文字流。

### D. 定价与计费

| 编号 | 约束 |
|---|---|
| D1 | 有效期一律写 **31 天**，全站**不出现"月"字和"自动续费"字样**（爱发电不支持包月，只能手动续） |
| D2 | Pro / Pro+ / Ultra 三档加**年包**，有效期 **372 天**，年包价 = 月包价 × 12 × 90~95% |
| D3 | 内置模型按 token 实时流计费，**预冻结 + 结算**，失败全额退回 |
| D4 | 账本用**不可变流水 + 行锁**，禁止直接 UPDATE 余额字段 |
| D5 | 爱发电归因走 **OAuth + 订单比对全自动发放**，不用二维码、不用兑换码 |
| D6 | 窗口大小当"上限"卖，**计费按实际携带量**；超出部分走 RAG 召回不进 prompt |

D6 是本轮唯一一处我改了用户字面选择的地方，原因是字面方案（按窗口大小卖到 1M + 全量携带）会让 D2 选的"静态前缀 + 提示词缓存"在最重度用户身上完全失效、越用越亏。用户已确认"冲突一：可以"。

## 4. 定价与权益矩阵

### 4.1 成本模型（先算清这个，定价才有意义）

DeepSeek Flash 现价约 `$0.14 / 百万输入 token，$0.28 / 百万输出 token`（调研值，**【必做】上线前以官网实时价校准**）。按汇率 7.1 折人民币：输入 ¥1.0/M，输出 ¥2.0/M。

一次典型对话轮次的真实消耗：

| 组成 | token | 成本 |
|---|---|---|
| 隐藏锁 prompt（静态前缀） | ~3,000 | 命中缓存后 ¥0.0001（缓存价约输入价 1/40） |
| 携带的历史消息 | ~8,000 | ¥0.0080 |
| RAG 召回片段 | ~1,200 | ¥0.0012 |
| 角色卡 + 系统层 | ~800 | ¥0.0008 |
| 输出 | ~600 | ¥0.0012 |
| **合计（未命中缓存）** | | **≈ ¥0.0112 / 轮** |
| **合计（静态前缀命中）** | | **≈ ¥0.0035 / 轮** |

> 这张表就是 D6 的由来：静态前缀命中与否，单轮成本差 **3.2 倍**。而命中与否取决于前缀是否一字不变——所以隐藏 prompt 必须"完全静态"，连时间戳都不能拼进去（时间戳放消息尾部）。这是 §7.2 专门讲的事。

**零售倍率定为 6×**（覆盖 embedding、TTS、存储、退款损耗和利润）。折算 **¥1 额度 ≈ 25 轮典型对话**。

**免费与付费的分界原则**（用户 B5 定案 + C.AI 教训）：
- 免费**必须能完整体验一次高质量对话**——包括隐藏锁 prompt、RAG 记忆、流式输出。这些是产品本体，锁掉就没人留下来付费。
- 付费买的是**规模与深度**：更多角色、更长记忆、更多召回、音色、皮肤、主动推送。
- 唯一硬锁的是**角色槽位 = 1** 和**携带量 = 8K**。"想多养几个 / 想让它记得更久"是天然的付费理由，且不会让免费用户体验显得残废。

### 4.5 UGC 卖卡

- 创作者自主定价，**平台抽成 30%**。
- 一期不做（C1 定案"导入放二期"，卖卡依赖导入与创作者工具，同属二期）。
- 二期上线时结算走爱发电：创作者各自的收款页，平台不碰资金池，只做抽成记账与展示。这是尚贤圈"平台不碰钱"模式的复用。

**分层职责一句话**：
- 前端（网页/安卓）只负责**渲染、输入、状态、体验**。
- Edge Function 负责**一切不能让用户看到的东西**：拼 prompt、解密 Key、调模型、算钱。
- 数据库负责**唯一真源**：对话、记忆、账本、社区内容。

## 7. 关键决策的理由（接手必读，别"优化"掉）

### 7.1 为什么聊天必须走 Edge Function，哪怕多一层延迟

因为用户要的是"用户绝对看不到、任何方式都查不到"的隐藏人设 prompt。只要 prompt 在浏览器里拼过，就一定能被 DevTools 抓到——这不是加固问题，是物理事实。同理，BYOK 的 Key 一旦下发到浏览器，就等于把用户的钱包暴露在 XSS 面前。

代价：多一跳网络延迟（Edge Function 冷启动约 100-300ms）。缓解：Edge Function 常驻 warm 实例 + 首字节前不等待业务写库（先连上流、边生成边落库）。

### 7.2 为什么隐藏 prompt 必须"完全静态"

提示词缓存的命中条件通常是**前缀完全一致**。这意味着：

- ✅ 隐藏锁 prompt、角色人设、示例对话 → 放在最前，**一个字都不变**
- ❌ 当前时间、用户名、剩余余额、随机 nonce → **绝对不能拼进静态前缀**

一旦你把"现在是 2026-09-26 21:30"塞进 system prompt 开头，缓存命中率归零，单轮成本从 ¥0.0035 涨回 ¥0.0112，**贵 3.2 倍**。重度用户每天 300 轮，就是每人每天 ¥2.3 的纯亏空。

需要动态信息时，放进**最后一条消息之前**，或用 RAG 片段的形式注入。

这条是本项目省钱的主牌，务必在代码 review 里守住。建议加一个构建期检查：静态前缀模板单独存文件，任何拼字符串进模板的行为直接 lint 报错。

### 7.3 为什么"窗口卖上限、计费按实际携带"

用户字面选的是"按窗口大小分层卖 1M"。但 1M 窗口若真全量携带历史，每轮输入近百万 token，缓存永远命不中（历史每轮都在变），成本会失控到无法定价。

改判后的做法：
- 用户看到的仍是"256K 档 / 1M 档"（营销分层不变）
- 实际进 prompt 的历史按 §4.4 的"携带量"控制（8K~512K）
- 超出部分走 RAG 召回（用户 C3 已经选了 RAG，天然接得上）
- 效果：用户仍觉得"它记得很久以前的事"（因为 RAG 召回了），但成本可控

### 7.4 为什么自建长连接还不够

用户 F2 选了自建长连接（避开厂商通道的账号成本），这个选择在他的约束下是对的。但必须知道它的失效条件：**国产 ROM 后台查杀**。进程被杀 = 长连接断 = 主动关怀消息收不到。

所以推送设计必须是**双层**：
1. **送达层尽力**：前台服务保活 + 唤醒锁 + 各 ROM 白名单引导页（不做静默保活，那是流氓行为，会毁口碑）
2. **真源层兜底**：所有主动消息先落库，客户端**打开时按时间戳补发**，并在应用内以"TA 想你了"的红点呈现

这样即使推送全挂，用户仍然会收到那条消息，只是晚一点。**绝不能把推送当成消息的投递保证**——消息的投递保证只能是数据库。

### 7.5 为什么建议留一个开发者个人号（用户已选官方号，这条只是提示）

抖音实测：爱语APP 是靠开发者本人 @无机化合物 的图文起家的（`我就这么宣传我自己做的APP` 6423 赞、更新日志、感谢信、"开发这个功能差点做死我"）。产品官方号在这个品类天然像公告栏，因为用户要的是"关系"，官方号给不了人格。

按用户定的做（官方号为主阵地），但建议同步养一个个人号做备用分发，零边际成本。**这是策略提示，不是反对。**

### 7.6 为什么免费用户只给 1 个角色槽位

不是抠，是**这个品类的付费理由必须建立在"我想再多养一个"上**。给 3 个免费槽位，付费转化率会掉一半；给 1 个，用户第一个角色养出感情之后，第二个角色的欲望就是最干净的付费触发点。

同时"1 个"不会让免费体验显得残废——一个人认真养一个角色，本来就用不满 3 个。

### 7.7 为什么角色卡要兼容 CCv2 但内部用扩展结构

CCv2（Character Card V2）是全网存量卡的通用格式。二期开导入时，兼容它 = 直接吃下整个社区现成的角色库，这是最便宜的冷启动燃料。

但 CCv2 装不下你要的玩法字段（好感度曲线、关系阶段、音色绑定、稀有度、群聊人设差异），所以内部结构必须自定义。**转换器放最后**：导入时映射能映射的、丢弃不能映射的并在 UI 上明示丢了什么；导出时反向映射。

## 8. 阶段划分（只谈先后与依赖，不谈时间）

顺序原则：**先让一次对话成立，再让它便宜，再让它记得，再让它主动，最后才谈钱和社区。**

| 阶段 | 内容 | 依赖 | 出口判据 |
|---|---|---|---|
| **P0 地基** | 仓库骨架、manifest、Supabase 项目、CI 部署 Pages、Auth（邮箱验证码）、设计 token | — | 手机和 PC 都能打开页面并登录 |
| **P1 对话内核** | Edge Function `chat`、静态前缀模板、流式回吐、断点续接、角色卡数据结构（不含 CCv2 转换） | P0 | 能和 1 个官方角色连续聊 50 轮不出戏 |
| **P2 成本闭环** | 提示词缓存命中验证、携带量控制、账本（不可变+行锁+预冻结结算）、DeepSeek Flash 接入、消耗可视化 | P1 | 单轮实测成本 ≤ ¥0.004；余额到 0 立刻停且不超付 |
| **P3 记忆** | pgvector + tsvector 混合检索、召回注入、事实抽取、召回条数分档 | P2 | 跨 200 轮后仍能准确召回早期细节 |
| **P4 角色锁定与养成** | 隐藏锁 + 防漂移拉回、内层好感度数值、外层关系阶段、100 条诱导回归测试集 | P3 | 诱导测试集通过率达标；用户无法从 UI 或网络面板拿到 prompt |
| **P5 多端与推送** | iOS WebApp 适配清单全过、Web Push、安卓原生（Kotlin+Compose）、自建长连接 + 补发、主动关怀 | P4 | 三端首屏与对话体验一致；杀进程后重开能补发全部消息 |
| **P6 售卖** | 爱发电 OAuth、订单比对自动发放、权益矩阵生效、加量包、管理后台 | P5 | 从付款到权益到账全自动、无人工 |
| **P7 社区与多模态** | 广场 + 评论 + 分享流、分享图生成器、立绘/表情包、TTS 音色、CCv2 导入导出、卖卡抽成 | P6 | 用户能一键生成漂亮分享图并导出 |

**并行说明**：P0 完成后，法律文本（27 篇）与命名定稿可与 P1-P2 并行推进，不占开发主线。

**为什么是这个顺序**：
- P2 排在 P3 前面，是因为成本模型必须先于记忆系统确定——RAG 召回条数直接决定 token 消耗，顺序反了 P3 会把 P2 的成果吃掉。
- P4 排在 P5 前面，是因为"不出戏"是产品成立的前提，比多端覆盖重要。
- P6 排在所有体验之后，是因为**在首次对话完成率没达标之前开始收费，等于花钱买差评**。
