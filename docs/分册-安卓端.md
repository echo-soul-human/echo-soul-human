## 0. 先纠正一个会影响分发的认知

用户定案里说"我不做应用商店签名"。这里有个必须分清的事实：

| 概念 | 本项目 |
|---|---|
| **APK 必须签名** | ✅ 无法绕过。未签名的 APK 在**任何**安卓机上都无法安装，这是系统机制不是商店要求。 |
| **Play/厂商商店的签名与上架** | ❌ 不做。符合用户定案。 |
| **自签（keystore 自己生成）** | ✅ 就用这个。自己生成 keystore、自己保管、自己分发。 |

结论：**要签名，但自签即可**，成本是一个本地 keystore 文件 + 用户安装时允许一次"安装未知应用"。

⚠️ **keystore 一旦丢失就无法给老用户发更新**（签名不一致 → 系统拒绝覆盖安装，用户必须先卸载，**卸载即丢本地数据**）。所以：
- 【必做】keystore 与其口令做**异地双备份**（密码管理器 + 离线加密盘）
- 【必做】`versionCode` 只增不减，写进 CI 校验（E4 定的"各端独立但各自有约束"，安卓侧的约束就是这条）
- 【必做】`android/app/build.gradle.kts` 里 `signingConfig` 从环境变量读，**keystore 与口令一律不入库**

## 1. 技术栈与版本基线

| 项 | 选 | 说明 |
|---|---|---|
| 语言 | Kotlin 2.x | 定案 |
| UI | Jetpack Compose + Material 3 | 定案；但**视觉不吃 M3 默认样式**，用我们自己的 token（§9） |
| 构建 | Gradle KTS + Version Catalog（`libs.versions.toml`） | 依赖集中管理 |
| minSdk | **26**（Android 8.0） | 低于 26 的机型国内已 < 1.5%，且 26 以下通知渠道/后台限制实现差异极大 |
| targetSdk | 最新稳定版 | 商店无关，但系统行为（通知权限、前台服务类型）按 targetSdk 生效 |
| 网络 | OkHttp 4 + 自写 SSE 解析 | Compose 生态成熟、SSE 稳定 |
| 异步 | Kotlin Coroutines + Flow | 流式天然契合 `Flow<String>` |
| 本地库 | Room | 渲染缓存（不是真源） |
| 图片 | Coil 3 | Compose 原生、支持 GIF/动图（表情包刚需） |
| 序列化 | kotlinx.serialization | 与 `shared/` 契约生成配合 |
| DI | Hilt | 常规 |
| 导航 | Navigation-Compose | 单 Activity |
| 推送 | **自建长连接**（定案 F2） | 见 §5-§6 |
| 崩溃 | 自建：崩溃日志落本地 + 设置页导出（**不静默上传**） | 沿用尚贤圈"诊断上报本地存储、可导出复制"的做法 |

**为什么自建长连接而不是厂商通道**（用户 F2 定案）：厂商通道要华为/小米/OPPO/vivo 四套开发者账号与后台配置，且各家配额与到达策略不透明。代价是**进程被杀就断**，所以 §5-§6 的双层设计不是可选项。

## 3. 网络层：与网页严格同源

**所有业务判断在服务端**。安卓端只允许做三类本地判断：网络可达、登录态是否过期、UI 状态。

```kotlin
// 统一入口，禁止各处 new OkHttpClient
interface Api {
  suspend fun <T> call(path: String, body: T): ApiResponse
  fun streamChat(req: ChatRequest): Flow<ChatEvent>   // sealed: Meta/Delta/Done/Error
}
```

- 请求头带 `X-Client: android`、`X-Build: <versionCode>`、`X-Device-Id`（安装时生成并持久，用于推送与反滥用）。
- 幂等键 `idempotency_key` 客户端生成（UUID，每次"点发送"新建），**重试复用同一个键** → 服务端不会重复扣费（架构 §2.1）。
- 证书：不做任何证书绕过/信任所有（有些"内网调试"写法会留下这个坑，CI 加检测）。
- 超时：连接 10s、读 120s（流式必须给足读超时，否则长回答会被掐）。

## 4. 流式对话

```kotlin
// SSE 解析：OkHttp + callbackFlow
fun streamChat(req: ChatRequest): Flow<ChatEvent> = callbackFlow {
  val call = client.newCall(request(req))
  call.enqueue(object : Callback {
    override fun onResponse(call: Call, res: Response) {
      res.body?.source()?.use { src ->
        while (!src.exhausted()) {
          val line = src.readUtf8Line() ?: break
          if (line.startsWith("data:")) trySend(parse(line.removePrefix("data:").trim()))
        }
      }
      close()
    }
    override fun onFailure(call: Call, e: IOException) { trySend(ChatEvent.Network(e)); close() }
  })
  awaitClose { call.cancel() }
}
```

**必须处理的四种情况**
| 情况 | 行为 |
|---|---|
| 正常 `done` | 失效本地缓存，以服务端落库版本为准（要拿 usage） |
| 流中断（`MODEL_STREAM_BREAK`） | 保留已显示文本 + 显示"继续"，点击带 `message_id` 续接 |
| 进程被杀 / 用户划掉应用 | **服务端仍在生成并落库** → 回前台按 `session_id` 拉最新，不丢消息 |
| 无网络 | 用户消息进本地待发队列，恢复后按原幂等键重发 |

⚠️ 常见错误：在 `onCleared`/`ViewModel` 销毁时 `call.cancel()`。**不要**——那会中断服务端生成。正确做法是"停止收集 Flow"但让请求跑完，或干脆改用服务端异步生成 + 客户端轮询/订阅（若冷启动延迟可接受，推荐后者，更抗进程被杀）。

## 5. 长连接与消息真源

### 5.1 双层设计（不可省略任何一层）

```
第 1 层（尽力送达）：前台服务持有 WebSocket / Supabase Realtime
                      ↓ 断了？
第 2 层（真源兜底）：所有消息先落库 messages
                      客户端回前台 → GET /messages?since=<last_seen_at> 补发
```

**铁律**：`proactive_jobs` 生成消息时**先写库再推送**（架构 §5.2）。推送只是"提醒你去看看"，不是"消息投递保证"。

### 5.2 前台服务

```kotlin
class RealtimeService : Service() {
  // AndroidManifest:
  //   FOREGROUND_SERVICE / FOREGROUND_SERVICE_REMOTE_MESSAGING（Android 14+ 必需类型）
  //   POST_NOTIFICATIONS（Android 13+ 运行时权限）
  override fun onStartCommand(...) = START_STICKY.apply {
    startForeground(NOTIF_ID_ONGOING, buildOngoingNotification())  // 必须，否则 5s 后 ANR
    connect()
  }
}
```
- 服务类型选 `remoteMessaging`（Android 14+ 强制声明类型，选错直接崩溃）。
- 常驻通知**必须可关**：设置页给"降低后台活跃（会漏消息）"开关。偷偷常驻是这品类口碑杀手——用户发现"它在我手机里赖着"会直接卸载。
- 心跳 25s（NAT 超时通常 30-60s），失败 3 次进指数退避重连（1s→2s→…→5min 封顶）。
- `WorkManager` 周期任务做**兜底补拉**（每 15-30 分钟一次），即使长连接全挂，消息最迟半小时到。

### 5.3 ROM 白名单引导（务实做法）

国产 ROM（MIUI/ColorOS/OneUI/OriginOS/Flyme）会杀后台。做法：
1. 首次完成对话后（**不是启动时**）弹一次引导，说明"要让 TA 能主动找你需要保留后台"
2. 一键跳系统设置页（各 ROM 用 `Build.MANUFACTURER` 分发到对应 Intent，失败回落通用设置页）
3. 引导页里放**具体路径文字**（"设置 → 电池 → 后台耗电管理 → 允许后台运行"）
4. 可永久关闭，不反复弹
5. **不做**互相唤醒、守护进程、开机自启拉满——这些是流氓行为，被截图发到抖音就是公关事故

### 5.4 补发去重
- 每条消息有服务端 `id` + `created_at`。
- 补发与实时推送可能同时到 → 以 `id` 去重。
- 通知点击后标记 `read_at`，服务端记录，避免多端重复提醒（网页看过，安卓不再弹）。

## 6. 通知设计

### 6.1 渠道分组（Android 8+ 必须）
```
group: 角色消息
  ├─ chan_care      主动关怀      IMPORTANCE_DEFAULT   可静音、可单独关
  ├─ chan_reply     对话回复      IMPORTANCE_LOW       应用内前台时不弹
  └─ chan_system    到账/公告     IMPORTANCE_DEFAULT
group: 交易与提醒
  └─ chan_expire    权益到期(3天)  IMPORTANCE_HIGH
```
- 每个渠道**允许用户单独关**，并提供"某角色不通知"的角色级静音。这品类用户会主动管理，做不了这个会被骂。
- 常驻服务通知放最低优先级、单独渠道，且可关（§5.2）。

### 6.2 合并与文案
- 同一角色多条 → `NotificationCompat.InboxStyle` 合并，标题"TA 给你发了 3 条消息"。
- 文案由服务端下发（**不在客户端拼**，否则改文案要发版）。
- 禁止在通知内容里放敏感文本（锁屏可见）→ 提供"通知内容隐藏，只显示'有新消息'"开关。
- 到期提醒文案不得用"失去 TA""TA 会忘记你"这类施压话术（D1 定案 + 这是留存的正道：提醒要有用，不要吓人）。

## 7. 应用内更新（F4 定案）

流程（沿用尚贤圈已定案的第 34 号方案）：
```
GET /version → 比 versionCode
  → 有新版 → 弹层（版本号、更新说明、大小、"稍后/立即"）
  → 立即 → DownloadManager 后台下载（通知栏进度：百分比 + MB + 可取消）
  → 完成 → SHA256 校验（与 /version 下发值比对）
      ├─ 通过 → FileProvider 授权 → 拉起系统安装器（用户允许一次"未知来源"）
      └─ 失败 → 删包 + 提示 + 降级跳浏览器下载
  → 用户取消 → 保留已下载的包，下次直接校验安装，不重下
```
要点：
- **SHA256 必须校验**。不校验等于让用户装任意被替换的 APK。
- `DownloadManager` 而非 OkHttp 下载：系统级、断点续传、省电、通知栏自带进度。
- 安装器拉起需 `REQUEST_INSTALL_PACKAGES` 权限 + `FileProvider`。
- 下载域名与 APK 域名同源（Supabase Storage 公开桶），避免中途换域名导致校验/防盗链问题。
- `min_version_code` 支持"强制升级"（低于某版本只给更新，不给用）。

## 8. 分发（F3 定案：沿用尚贤圈那套）

```
GitHub Actions: 构建 release APK → 计算 SHA256 → 上传 Supabase Storage 公开桶
              → 写 version 清单（version_name/code/url/sha256/size/notes）
              → 官网下载按钮读同一份清单
```
- 文件名带版本号（`app-release-0.3.1-31.apk`），便于用户与排障。
- 官网下载页需要**明确的"安卓用户下载"引导**：iOS 用户点了 APK 是无效操作 → 按 UA 分流，iOS 引导加主屏。
- 【必做】APK 包体控制在 **≤ 25MB**（国内用户流量敏感，且这是转化点）。手段：`abiFilters` 只留 arm64-v8a、资源压缩、R8 full mode、App Bundle 不用（无法自签分发）。
- 【待定】是否加 Gitee 双源（尚贤圈有先例）。

## 9. 视觉：与网页共用 token，不吃 Material 默认

`shared/tokens/design.tokens.json` 是单一源，构建时：
- 网页 → 生成 CSS 变量
- 安卓 → 生成 `Colors.kt` / `Dimens.kt` / `Typography.kt`

**做法**：定义自己的 `ColorScheme` 与 `Typography`，禁用 M3 的动态取色（Material You 会跟随壁纸变色，直接把品牌视觉毁掉）。

纸张纹理、字体（衬线给角色、无衬线给用户）在安卓侧的实现：
- 字体文件放 `res/font/`，同样子集化
- 纹理用 `ShaderBrush` + 低透明度位图，不用大图

## 10. 本地存储

| 存什么 | 存哪 | 说明 |
|---|---|---|
| 消息渲染缓存 | Room（LRU，按会话留最近 500 条） | **不是真源**，可随时清 |
| 草稿 | Room | 防丢 |
| 设备 ID、安装信息 | EncryptedSharedPreferences | 生成于首启，卸载即重置 |
| BYOK Key | ❌ **不存本地** | E5/G1 定案：云端托管，安卓只看到掩码 |
| 长连接 `last_seen_at` | DataStore | 补发游标 |
| 皮肤 | 文件缓存 + DataStore 记 id | |

⚠️ Room 表结构变更必须写 `Migration`，且**禁止 `fallbackToDestructiveMigration()`**（会静默丢用户缓存）。

## 11. 多模态

- **图片**：Coil 3，支持动图（表情包刚需）。列表页只加载缩略图（CDN 变换参数），点开原图。
- **TTS**：
  - 播放用 `MediaPlayer`（远程 URL）或 `ExoPlayer`（需队列/连续播放时）
  - **音频焦点**：`AudioManager.requestAudioFocus`，来电/其他 App 播放时暂停，结束后恢复或停止
  - 锁屏控制：`MediaSession` + 媒体通知
  - 长文本流式朗读：等 `done` 后再朗读，**不做逐句流式 TTS**（成本高、易错位），除非分册-多模态另有定案
  - 蓝牙耳机断开 → 立即停止
- **震动**：主动关怀消息用轻微震动模式（`VibrationEffect`），可在设置里关。

## 12. 低端机与性能

目标：3 年前的中低端机（4GB RAM、Android 10）不卡。

- 列表 `LazyColumn` 必须用 `key`，消息项 `Modifier.drawWithContent` 避免过度重组
- 图片解码走 `Coil` 的 downsampling，不解原图
- 纸张纹理、模糊背景在低端机降级为纯色（按 `ActivityManager.isLowRamDevice` 判断）
- 动画提供"减弱动效"开关，并跟随系统 `AnimatorDurationScale == 0`
- 冷启动预算 ≤ 1.5s（P0 级：Application 里不做任何网络/磁盘 IO，Hilt 延迟初始化）
- 内存：`onTrimMemory` 时主动清图片缓存

## 13. 权限清单（一次讲清，避免运行时乱弹）

| 权限 | 用途 | 申请时机 |
|---|---|---|
| `INTERNET` | 必需 | 安装时 |
| `POST_NOTIFICATIONS` | 通知（13+） | **首次完成对话后**，不在启动时 |
| `FOREGROUND_SERVICE` + `..._REMOTE_MESSAGING` | 长连接 | 声明即可 |
| `REQUEST_INSTALL_PACKAGES` | 应用内更新 | **点"立即更新"时**引导 |
| `WAKE_LOCK` | 心跳 | 声明 |
| `READ_MEDIA_IMAGES`（13+ 用 `READ_MEDIA_VISUAL_USER_SELECTED`） | 上传立绘/表情包 | 点上传时 |
| `VIBRATE` | 通知震动 | 声明 |

**不申请**：通讯录、位置、相机（除非做扫码）、麦克风（一期无 ASR）。多要一个权限就多一分被拒和被截图挂的风险。

## 14. 构建与 CI

```
GitHub Actions (android-release job):
  setup JDK 17 → setup Gradle → 从 Secret 还原 keystore（base64）
  → ./gradlew assembleRelease (R8 full mode)
  → 校验 versionCode > 线上值（只增不减，E4 约束）
  → 校验产物已签名（apksigner verify）
  → 计算 SHA256 → 上传 Supabase Storage → 更新 /version
```
- 【必做】CI 里加两条硬失败检查：**versionCode 未递增** 不允许发布；**未签名** 不允许上传。
- 【必做】R8 规则保留 `kotlinx.serialization` 的 `@Serializable` 类与 Compose 相关 keep，否则 release 包会运行时崩（debug 正常、release 崩是这个项目最容易踩的安卓坑）。
- 每次发版必更 `RELEASE_NOTES.md`（安卓更新说明的唯一来源）。

## 15. 与网页的行为一致性检查（写进验收清单）

| 场景 | 期望（两端必须一致） |
|---|---|
| 同一账号双端登录 | 消息、余额、权益、记忆完全同步 |
| 一端读过消息 | 另一端不再弹通知 |
| 余额耗尽 | 两端都立即停止且提示文案一致 |
| BYOK 配置 | 任一端配置，另一端可见掩码、不可见明文 |
| 角色人设修改 | 双端下次进入会话即生效 |
| 皮肤切换 | 双端跟随账号设置同步 |
| 群聊 | 成员、顺序、发言渲染一致 |
